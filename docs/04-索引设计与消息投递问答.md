# 索引设计与消息投递问答

> 开发答疑记录，作为 [02-表结构说明](02-表结构说明.md) 的补充理解材料。
> 索引的场景备注已同步写入 [V1__init_schema.sql](../src/main/resources/db/migration/V1__init_schema.sql) 各索引行尾。

## 1. 二级索引基础：B+ 树结构与排序

### 1.1 两棵树

InnoDB 每张表至少两棵 B+ 树：

```text
聚簇索引（PRIMARY KEY）          二级索引（如 idx_receive_status）
┌─────────────────────┐        ┌──────────────────────────┐
│ 叶子节点 = 完整一行数据 │        │ 叶子节点 = 索引列的值 + 主键id │
│ 按 id 排序            │        │ 按索引列组合排序             │
└─────────────────────┘        └──────────────────────────┘
```

二级索引叶子节点不存整行，只存 `(索引列1, 索引列2, ..., 主键id)`。用二级索引查到位置后要取其他字段，得拿 id 回聚簇索引再查一次——"回表"。

### 1.2 排序规则：字典序

以 `friend_apply` 的 `idx_receive_status (receive_user_id, status, create_time)` 为例，叶子条目物理存放顺序：

```text
(1001, 0, 2026-11-01 10:00, id=5)
(1001, 0, 2026-11-02 09:30, id=11)
(1001, 0, 2026-11-03 08:00, id=20)   ← receive=1001, status=0 的区段（连续！）
(1001, 1, 2026-10-20 14:00, id=3)
(1002, 0, 2026-11-04 12:00, id=15)
```

先按第 1 列排，相同再按第 2 列，再按第 3 列，最后按 id 决胜。三个推论：

1. **等值条件钉住前几列后，命中区段在索引里是连续的**；
2. **区段内天然按后面的列排好序**——`ORDER BY create_time DESC LIMIT 20` 零 filesort，直接从区段尾部倒读；
3. **范围条件是截断点**——某列用了 `>`/`<`/`LIKE 'x%'`，它之后的列失去排序约束。

### 1.3 最左前缀

`WHERE status = 0`（不带 receive_user_id）用不上该索引：树按第 1 列分叉，跳过第 1 列无处定位。低区分度的状态列**单独**建索引几乎无价值，它的价值要和排序列绑在一起才兑现（`idx_status_create` 的价值全在第二列的时间排序上）。

### 1.4 设计三规律

1. **等值列在前，排序列在后**（规约索引第 5 条：order by 字段放组合索引末尾，避免 filesort）；
2. **索引服务于具体 SQL**——建索引前先写下它服务的 SQL，写不出来的不要建；
3. **一棵树只有一种排列**——同一列组从两个方向查就建两棵树（`user_friend` 两个索引、`group_member` 的 `idx_user_status`/`idx_group_status` 同理）。

## 2. 逐表索引场景速查

| 索引 | 模式 | 服务场景 |
|---|---|---|
| `user_account.idx_status_create` | 等值+排序 | 后台按状态筛选、按注册时间分页 |
| `user_device.idx_user_active` | 等值+排序 | 推送选最近活跃设备（区段尾部第一条） |
| `friend_apply.idx_receive_status` | 等值+等值+排序 | "新朋友"页：收到的申请 |
| `friend_apply.idx_apply_user` | 等值+排序 | "我发出的申请"进度列表 |
| `user_blacklist.idx_blocked_user` | 单列反查 | 谁把我拉黑了 / 注销清理 |
| `group_member.idx_user_status` | 反方向 | "我加入了哪些群"（侧边栏） |
| `group_member.idx_group_status` | 正方向 | 群成员列表；群消息投递拉"在群成员"名单（每发一条消息都查） |
| `group_apply.idx_group_status` / `idx_apply_user` | 与 friend_apply 同构 | 群主看申请 / 申请人看进度 |

要点：

- `group_member.idx_group_status` 与 `uk_group_user` 同首列但不冗余：uk 第二列是 user_id，status 在区段里散乱，过滤要逐行回表；idx 第二列是 status，过滤在索引内完成，只取 user_id 的查询还覆盖索引不回表；
- `group_info.uk_group_no`：群号是对外短号（QQ 群号那种），给人搜、给人报；雪花 ID 是对内关联用的。id 是机器用的，group_no 是人用的。

## 3. 消息水位（watermark）

一条只涨不降的刻度线，标记"到这里为止都处理过了"。`conversation_member` 三根水位线：

```text
会话消息流（seq 单调递增）： 1 ─ 2 ─ 3 ─ 4 ─ 5 ─ 6 ─ 7
last_delivered_seq = 4   已推送到客户端（推送水位）
last_read_seq      = 6   用户读到这里（已读水位）
deleted_seq        = 2   用户清空会话到这里（删除水位）
```

全部是纯数字运算，不扫消息表：

```text
未读数   = max_seq - last_read_seq
离线补拉 = seq > last_delivered_seq 的消息
清空会话 = deleted_seq = 当前 max_seq，旧消息不再拉给这个人
```

`chat_message` 全局一份消息，每个人靠自己的水位线决定看到什么——"消息全局一份，每人一份游标"。

## 4. client_msg_id 与发送幂等

**client_msg_id**：客户端每次点"发送"按钮时生成的幂等键（UUID），随消息发给服务端。它的生命周期 = 一次发送动作。

弱网场景：发出去 → ACK 半路丢 → 客户端没等到 ACK **自动重发同一包（同一个 client_msg_id）**，SDK 层重试用户无感知；全失败后气泡变红色感叹号，用户点"重发"本质也是原消息+原幂等键再交一次。用户故意连发两条相同内容是两次发送动作、两个新幂等键，正常发出去——防的是"一次发送在网络层重复到达"，不是"用户发两条相同内容"。

**uk_sender_client (sender_id, client_msg_id)**：数据库兜底。重发再 INSERT 撞 `Duplicate key` → 服务端查出第一次那条原样返回。组合键带 sender_id 是因为 client_msg_id 只在单个客户端范围有意义，防不同用户的本地 ID 撞车。协议在客户端、防线在唯一索引（规约【强制】：业务唯一字段必须建唯一索引）。

## 5. 消息引用存在哪

不是 `message_mention`（那是 @提醒表）。**引用放在 `chat_message.content` JSON 结构里**，文本类消息多带一个 quote 对象：

```json
{
  "type": "text",
  "text": "收到，明天发你",
  "quote": { "message_id": 123, "sender_id": 10001, "preview": "合同初稿在附件里" }
}
```

存 `preview` 快照是因为被引用消息可能已被撤回/删除，快照保证引用气泡永远显示得出来。引用功能在"后续迭代"，`content` 是 JSON 结构化列，届时加 quote 字段表结构零改动。

## 6. event_outbox：本地消息表 / Outbox 模式

解决的问题：**"消息存进库了，但后续动作丢了"**。

发群消息后还有一串后续：更新各成员未读数 → Netty 推在线设备 → 厂商通道推离线设备。若落库后直接顺手做，中途进程崩溃，消息就成了黑洞——存了但没人收到，且无机制知道没做完。

解法：**把后续动作当一行数据，与消息同一事务写入 outbox**：

```sql
-- 同一事务，要么都成要么都不成
INSERT INTO event_outbox (event_type, aggregate_id, payload, status, ...)
VALUES ('MESSAGE_DELIVER', 消息ID, '{"conversationId":501,"seq":88,"memberIds":[...]}', 0, ...);
```

异步线程周期扫描投递（`idx_status_next` 服务的就是这条）：

```sql
SELECT * FROM event_outbox
WHERE status IN (0, 2) AND next_retry_time <= NOW()
ORDER BY next_retry_time LIMIT 100;
```

成功 → `status=1`，定期按 `create_time` 归档清理（`idx_create_time`）；失败 → `retry_count+1`、`next_retry_time` 退避重试。

字段角色：`event_type`=干什么、`aggregate_id`=针对谁、`payload`=全部原材料（下游不用回查）、`retry_count/next_retry_time`=失败退避。类比外卖小票：点单和打小票同一秒完成，后厨照小票做菜，小票在单就不丢。

价值一句话：消息落库成功即代表"后续动作一定会发生"——把"恰好完成"变成"最终完成"。拆微服务时异步投递换成投 MQ，消费者变独立服务，Outbox 是现成过渡件。

## 7. 推送链路：长连接是"信"，厂商通道是"铃"

所有消息都落库，不同状态的设备用不同方式拿到它：

| 端 | 实时通道 | 说明 |
|---|---|---|
| PC（Electron）/ Web | Netty 长连接（TCP/WebSocket） | 桌面端可常驻，连接一直挂着 |
| iOS | 前台 Netty；后台只能 APNs | iOS 不允许后台常驻进程，长连接会被系统挂起 |
| Android | 前台 Netty；被杀走厂商通道 | 国内无 FCM，华为/小米/OPPO/vivo/荣耀/EMAS——`user_device.push_provider` 枚举的来源 |

厂商通道推的**只是提醒**（发送人+摘要，受系统推送大小限制），真正的消息体在库里。用户点提醒 → App 拉起 → 连长连接 → 走离线补拉（`seq > last_delivered_seq`）拿真消息。

```text
在线设备：Netty 直推（信）
离线设备：厂商通道发提醒（铃）→ 用户点开 → 补拉真正的消息
```

第一阶段范围：Netty 长连接为主，离线用户靠上线补拉；EMAS/厂商推送在"后续迭代"。

## 8. 多端已读同步：PC 读了，手机算已读还是未读

**结论：已读，未读数归零**——与微信行为一致（PC 看完消息，手机上的红点会消失）。

原因：**已读状态是按"人"存的，不是按"设备"存的**。`conversation_member` 一个成员一行，只有一根 `last_read_seq` 水位线，多端共享。PC 端读到 seq=6，服务端把 `last_read_seq` 推到 6，此后：

```text
未读数 = max_seq - last_read_seq = 7 - 6 = 0   ← 手机拉会话列表时算出来也是 0
```

手机端角标的清除时机有两种：

1. **实时**：服务端在 PC 已读后向该用户其他在线端推一条"已读变更"同步事件，手机端收到立即把角标清掉（体验最好，做不做是客户端迭代问题，表结构已支持）；
2. **兜底**：手机端下次拉会话列表/补拉时，按服务端最新 `last_read_seq` 重算未读数，自然归零。

### 如果想"各端各读各的"（手机保持未读）怎么办

那就得把 `last_read_seq` 挪到按设备存（`conversation_member` 拆出设备维度），未读数取各设备最小已读水位。微信式体验（多端共享已读）是主流选择，本项目选按人存。设计取舍先记录在此，若产品后期要求独立已读再演进。
