# 扩容与微服务演进路线

> 结论：V1 表结构已为分库分表和微服务拆分预留了路，**当前阶段按单体单库开发**，不为未来量级提前引入分布式复杂度（阿里规约：预计三年达不到的量级，不要在建表时分库分表）。
> 本文档记录目标量级、逐表体检结论、升级路径与各阶段的触发时机。

## 1. 目标量级与瓶颈位置

| 口径 | 瓶颈位置 | 表结构 |
|---|---|---|
| 千万注册用户、日活百万~千万 | `chat_message` 数据量（几十亿行） | 不改结构，只需分表 |
| 千万级同时在线（微信量级） | 接入层连接数、消息写入吞吐 | 不改结构，链路改造（MQ 削峰、多级缓存、读写分离）为主 |

两种口径下瓶颈都是"数据放得下吗、写得进吗"——是分片问题，不是 schema 问题。

## 2. 逐表体检结论

**单表够用，不用动**（千万行级别，MySQL 8 性能无实质衰减）：
`user_account`、`user_profile`、`user_setting`、`group_info`、`group_apply`、`friend_apply`。

**时间归档/清理即可**（滚动窗口，不分片）：
`sms_record`（按月归档删旧）、`event_outbox`（投递完就清）。

**真正要分片的只有 3 张：**

| 表 | 分片键 | 说明 |
|---|---|---|
| `chat_message` | `conversation_id` | `uk_conversation_seq (conversation_id, seq)` 首列即分片键，按会话 hash 分表后所有高频查询（补拉、历史、幂等）都落在单分片内，schema 零改动 |
| `conversation` | `conversation_id`（主键即分片键） | `max_seq` 更新、会话详情都是单键查询 |
| `conversation_member` | `user_id` | 唯一小别扭的表，见下 |

`conversation_member` 的别扭：会话列表按 `user_id` 查（`idx_user_update`），群已读/写游标按 `conversation_id` 查（`uk_conversation_user`），按 `user_id` 分片后游标更新会跨片。**解法**：游标更新统一改为 `WHERE user_id = ? AND conversation_id = ?`（语义等价），全部单分片。这是代码改动，不是表改动。

其余按 `user_id` 分即可（`user_friend`、`group_member`、`user_device`、`message_mention`），唯一索引首列均已含 `user_id`。

## 3. V1 中已埋好的伏笔

| 设计 | 为升级省的钱 |
|---|---|
| 无外键（V1 头部约定 1） | 分片零阻碍，关联全在应用层 |
| 对外实体用雪花 ID | 分库后自增必冲突，雪花跨库唯一，迁移不用改 ID |
| per-conversation `seq` | 消息顺序只依赖 `(conversation_id, seq)` 局部序，不依赖全局时钟/号段 |
| `conversation` 冗余 `last_message_*` | 会话列表不 join 消息表；分片后跨片 join 是最痛点，核心链路本来就没有 join |
| `event_outbox` | 拆微服务时"落库→下游"解耦机制现成，消费者直接变独立服务 |

## 4. 升级路径

```text
阶段0（现在，单体单库）        ← 当前状态，啥都不用做
阶段1（垂直拆库）              按域拆：account库 / relation库 / im库
                              → 每个域本来就是独立表集合，搬库即可，Flyway 按库分组
阶段2（消息表水平分表）        chat_message 按 conversation_id hash 16/64 张表
                              → 只改 Mapper 路由，schema 零改动
阶段3（水平分库 + 读写分离）   再按 user_id/conversation_id 分库
                              → 双写 + 灰度迁移，老表保留兜底
阶段4（拆微服务）              按域拆服务，outbox 事件变成跨服务消息
```

每一步都是加法（新库、新表、新服务），不是对现有结构的否定性重构。成本最高的在第 3 阶段的双写迁移，但那是任何 IM 到该量级都要付的固定成本。

## 5. 现在就要做的两件小事

1. **workerId 用 Redis 分配**：写发消息代码时，workerId 走 Redis（`SETNX` 抢号 + 心跳续期）分配，避免集群/容器扩缩容撞号；
2. **守住分片键纪律**：所有 `chat_message` 查询都带 `conversation_id` 条件，分片键永远不会被绕开。

不建议现在做的：提前分库分表、提前拆微服务。

## 6. 量级预期管理

若目标真是**千万同时在线**，MySQL 只是链路一环，改造量比表结构大的有：Netty 接入集群（连接按 user 一致性哈希路由）、Redis 集群存在线路由表、消息写入走 MQ 削峰——这些属于阶段 4 之后的事。
