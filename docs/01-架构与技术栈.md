## 0. 结论先行

1. **架构形态：模块化单体（Modular Monolith）起步，不上微服务。**
   一个可部署单元同时提供 HTTP API 和 Netty WebSocket；内部按业务域分包、禁止跨域直接查表；预留三个拆分点：WS 接入层、消息投递服务、朋友圈 Feed 服务。

2. **技术栈：JDK 21 LTS + Spring Boot 4.1.x + MyBatis-Plus 3.5.18 + MySQL 8.0 + Redis 7 + Netty 4.2 + 阿里云 OSS/CDN/短信。**
   RocketMQ、Sentinel、Elasticsearch 按阶段引入；Spring AI 2.x / agent-utils 后期接入，技术栈提前对齐。

3. **容量要说清楚：8 核 4G 不是百万在线的机器。**
   8C4G 跑业务 + WS 的舒适区约 **2～3 万在线**；只做 WS 接入、低消息率、调优后可以到 **5～10 万在线**，但没有余量；**十几万（10 万+）必须 8C16G 或多节点**。
   百万“同时在线”至少需要 **20～50 个接入节点** + 独立网关 + 消息队列 + 分库分表。**百万级是架构演进目标，不是首台服务器的验收指标。**
   扩容验收线建议：**2 个 8C4G 节点 + SLB，合计 5～10 万在线、1k msg/s**。
   **当前预算阶段：1～2 千在线，1 台 4C8G 全栈（jar + MySQL + Redis）足够**；若做 1～2 万在线，用 1 台 8C16G 全栈或 8C8G + 云 RDS/Redis。

4. **数据模型核心：`conversation` + `conversation_member` + `chat_message(seq)` 三张表。**
   未读/已读统一用 `last_read_seq`；离线同步用 seq 游标；不再依赖 `last_off_time`，不再一次性推全量离线消息。

5. **必须从 v1 修正的六件事：**
   seq 游标、服务端未读数（已读回执后续）、WS 路由而非全局广播、文件 OSS 直传、手机号短信注册、消息幂等与 outbox。

6. **已拍板：** 近期不做百万在线，先按 **5～10 万在线** 设计；当前预算先按 **1～2 千在线** 验收，用 **1 台 4C8G 全栈（jar + MySQL + Redis）**，1～2 万在线再升 8C16G；技术栈 **JDK 21 + Spring Boot 4.1.x**；客户端为 **Electron + 移动 App**，多端同时在线；**单聊/群聊都做未读数**，已读回执后续做；**不兼容 v1 前端/API**；短信使用 **阿里云号码认证服务 Dypnsapi**；当前只做 IM 基础功能，进阶功能后续迭代。

## 1. v1 盘点：哪些可以继承，哪些必须重做

### 1.1 v1 已实现能力

| 域 | 能力 | v1 实现方式 |
|---|---|---|
| 账号 | 邮箱注册、登录、图形验证码、退出、改密 | `user_info` + Redis token |
| 联系人 | 搜索、申请、同意/拒绝、删除、拉黑 | `user_contact` 双行状态 |
| 群 | 建群、加人、踢人、退群、解散、群公告、群昵称 | `group_info` + 复用 `user_contact` |
| 会话 | 会话列表、最后一条消息 | `chat_session` + `chat_session_user` |
| 消息 | 单聊、群聊、文本、图片/视频/文件、机器人 | `chat_message` + Netty WS |
| 文件 | 上传、下载、封面 | 本地磁盘 `D:/wechat/` |
| 集群 | 多实例广播 | Redis Topic + 本机 Channel 表 |
| 运营 | App 更新、系统设置、靓号 | `app_update`、`user_info_beauty` |

### 1.2 v1 在规模化时会暴露的问题

| # | 问题 | 后果 | v2 做法 |
|---|---|---|---|
| 1 | 离线消息靠 `user_info.last_off_time` 时间戳 | 非正常下线时间不准；同毫秒消息、时钟回拨不可靠；超 3 天直接丢 | 每会话单调 `seq`，客户端上报 `last_seq` 增量拉取 |
| 2 | 登录 INIT 一次性推所有离线消息 | 离线久了 payload 巨大；前端未读数重复累加；消息漫游做不了 | INIT 只返回会话列表 + 未读数 + `maxSeq`；消息按会话分页拉 |
| 3 | 未读数只在前端 SQLite | 多端各自为政；服务端无法做已读、漫游 | `conversation_member.last_read_seq`，未读 = `max_seq - last_read_seq` |
| 4 | `contactId` 一字段两用（路由目标 / 会话对象） | 代码语义混乱，推送前要覆写，特例越加越多 | 拆 `receiverId`（内部路由）与 `conversationId`（对外会话） |
| 5 | 群成员复用 `user_contact(contact_type=GROUP)` | 状态 0～5 承担多义；退群/踢人物理删除；成员数统计不准 | 独立 `group_member`，逻辑删除 + 重新入群 upsert |
| 6 | 单用户只保留一条连接，后登录顶掉前一个 | 手机 + 桌面不能同时在线；多端已读无法同步 | `userId + deviceId` 维度连接，多端在线，按设备同步 |
| 7 | 全局 Redis Topic 广播到所有实例 | 节点越多广播越贵；与接收人无关的节点也收消息 | Redis 路由表 `ws:route:{userId}:{deviceId} -> nodeId`，按节点投递 |
| 8 | Redis Pub/Sub 是发后即忘 | 发布失败/实例抖动会丢推送 | 关键事件走 `event_outbox` + 重试；客户端 seq 拉取兜底 |
| 9 | 文件落本地磁盘，下载走应用接口 | 应用服务器带宽/磁盘成瓶颈；扩容要共享存储 | 前端拿预签名 URL 直传 OSS；CDN 签名读取 |
| 10 | 密码 MD5(32) | 可离线爆破 | BCrypt |
| 11 | WS token 放在 URL 查询串 | token 进 Nginx/网关日志，易泄露 | 先换一次性 `wsTicket`，再建立 WS |
| 12 | 消息没有幂等键 | 客户端重试产生重复消息 | `sender_id + client_msg_id` 唯一索引 |
| 13 | 媒体消息先落“发送中”再传文件 | 断网/取消留下半条消息；状态机复杂 | 先传文件拿 `file_id`，再发消息 |
| 14 | 无撤回/删除/引用字段 | 新需求无法承载 | 状态位 + `quote_message_id` + 快照 |
| 15 | 无内容审核 | 合规风险 | 文本敏感词 + 图片/视频内容安全异步审核 |
| 16 | 配置里明文数据库密码 | 违反阿里手册安全规约 | KMS / Jasypt 加密，环境变量注入 |
| 17 | `System.out.println`、`insertIgnore` 等 | 日志不可控；错误被吞 | SLF4J + 明确 upsert 语义 |
| 18 | fastjson2、easy-captcha + Nashorn 兼容层 | 额外依赖与维护成本 | 新工程用 Jackson；v2 不做图形验证码，统一短信验证码 + 限流 |

> 结论：v1 的**业务语义**可以继承，**存储模型和推送模型**必须重做。不要在原表上“打补丁式”加字段，否则历史包袱会带进 v2。

## 2. 容量口径与服务器现实

### 2.1 先把“并发”拆开

| 指标 | 含义 | 典型关系 |
|---|---|---|
| 注册用户 | 累计账号数 | 不等于在线 |
| DAU | 日活 | 通常 10%～30% 注册量 |
| 同时在线连接 | WebSocket 长连接数 | DAU 的 5%～20%（IM 类可能更高） |
| HTTP QPS | 每秒接口请求 | 与在线数、刷新频率相关 |
| 消息 TPS | 每秒写入/投递消息数 | 与在线数、发送频率相关 |

“百万级并发”如果指 **100 万同时在线**，按每人每分钟 1 条消息估算：

```
100 万在线 / 60 秒 ≈ 1.67 万 msg/s（平均）
按峰值 3 倍 ≈ 5 万 msg/s（峰值）
```

这需要独立的消息接入、投递、存储、审核链路，不是一台 8C4G 能承担的。

### 2.2 8C4G 的真实能力（保守估计）

| 场景 | 8C4G 现实能力 |
|---|---|
| 1～2 千在线、低消息率 | **很轻松**；CPU/内存都有大量余量，瓶颈通常先出现在 MySQL/Redis 或带宽 |
| 业务 + WS 同进程，正常消息率 | **2～3 万在线**，这是推荐的生产舒适区 |
| 专用 WS 接入进程，低消息率，充分调优 | **5～10 万在线**，但没有余量，故障/活动峰值容易顶满 |
| 10 万以上在线 | 8C16G 或 2 个以上节点；**8C4G 不建议硬扛十几万** |
| HTTP QPS | 简单读接口 1～3k；带 MySQL 写 300～1k；有缓存可更高 |
| 消息 TPS | 单 MySQL 主库 + 合理索引，约 500～2k（取决于事务和索引数） |
| 内存瓶颈 | 4G 中 JVM 最多 2.5～3G；10 万连接仅 Channel/Pipeline/会话对象约 0.5～1G，加直接内存、内核 socket、GC 余量，4G 很紧 |
| 建议 | **WS 场景内存 > 核数。预算固定时，4C8G 比 8C4G 更合适。** 生产不建议 MySQL/Redis 与应用挤在同一台 4G 机器 |

> “十几万并发”要拆开看：**10 万空闲长连接**在专用 WS 节点上勉强可行；**10 万 QPS 或 100 万同时请求**，8C4G 完全不可能，必须网关限流 + 队列 + 集群。在线连接和请求并发是两类问题，不要混在一起做容量承诺。

### 2.2.1 单机 1～2 千 / 1～2 万在线怎么配（成本优先）

如果只买一台服务器，按目标 **1～2 千或 1～2 万同时在线** 选配：

| 方案 | 配置 | 说明 |
|---|---|---|
| **1～2 千在线（已选）** | **4C8G 全栈（jar + MySQL + Redis）** | JVM 3G、MySQL 1.5～2G、Redis 512M～1G、OS/页缓存 1.5～2G；磁盘 100～200G ESSD |
| 1～2 千在线（备选） | 8C4G 应用 + 云 RDS/Redis | 更稳，但要多买 RDS/Redis；8C4G 只跑应用余量很大 |
| 全栈单机（1～2 万） | **8C16G** + ESSD 200～500G + 20～50Mbps | 应用 + MySQL + Redis 同机；JVM 6～7G、MySQL 3～4G、Redis 1～2G、系统/页缓存 2～3G |
| 应用单机 + 云服务（1～2 万） | **8C8G**（或 4C8G）+ 云 RDS 2C4G + 云 Redis 2G | 更稳，数据库有备份/主从；总成本可能和 8C16G 接近 |

结论：
- **1～2 千在线：4C8G 全栈已选**；4 核跑 1～2 千长连接和低消息率够用，关键是内存分配不要超卖。
- **1～2 万在线、单机全栈：最低舒适配置是 8C16G**；如果只能 8C4G，就把 MySQL/Redis 拆出去，并且只按 1 万左右在线做保守承诺。

> 注意：1～2 千“高并发”要区分口径：
> - **1～2 千同时在线连接**：8C4G 只跑应用很轻松；
> - **1～2 千 QPS**：简单读接口有 Redis 可以，写接口受 MySQL 限制（单主库约 300～1k TPS），需要压测；
> - **1～2 千瞬时并发请求**：短请求可以，慢 SQL/大事务会拖垮连接池，必须限流 + 超时 + 索引。

### 2.3 分阶段容量规划

| 阶段 | 注册用户 | DAU | 峰值在线 | 峰值消息 | 部署 |
|---|---|---|---|---|---|
| MVP | 1 万 | 1k | 1k | 50/s | 1×4C8G 全栈（jar + MySQL + Redis） |
| **1～2 千在线（当前预算）** | 1～2 万 | 1～2 千 | **1～2 千** | 50～100/s | **1×4C8G 全栈（jar + MySQL + Redis）**；备选 8C4G + 云 RDS/Redis |

| 近期目标 | 200 万 | 20 万 | **5～10 万** | 500～1k/s | **2×8C4G 应用（SLB 双活）** + RDS 2C4G/4C8G + Redis 2G |

### 2.4 数据量预估

按单条约 500B（含索引约 1KB）估算：

| DAU | 人均消息/天 | 日增消息 | 日增存储（含索引） | 年增 |
|---|---|---|---|---|
| 1 千 | 50 | 5 万 | ~0.05 GB | ~18 GB |
| 1 万 | 50 | 50 万 | ~0.5 GB | ~180 GB |
| 10 万 | 50 | 500 万 | ~5 GB | ~1.8 TB |
| 100 万 | 50 | 5000 万 | ~50 GB | ~18 TB |

结论：
- `chat_message` 必须从第一天就按 **conversation_id 查询 + (conversation_id, seq) 索引** 设计；
- 超过 500 万行/2GB 后再考虑分表（阿里手册建议），但**分片键必须提前选好**：按 `conversation_id` 哈希；
- 冷热分离：当前采用微信式，服务端热库保留 3 天，历史以客户端本地为主；后期升级到 90 天/6 个月时再启用归档任务。

## 3. 总体架构

### 3.1 设计原则

1. **单体优先，但边界清晰**：一个部署单元，按业务域分包；域之间只通过 Service 接口/事件交互，不跨域直接写表。
2. **无状态 HTTP，有状态 WS**：HTTP 节点可随意扩缩；WS 节点持有连接，必须能路由、能迁移、能故障摘除。
3. **DB 是事实来源，Redis 是加速与路由**：未读、在线、路由可以短暂不一致，消息和会话关系必须以 DB 为准。
4. **至少一次投递 + 客户端去重 + seq 补拉**：不追求“绝不重复”，追求“可恢复、可去重”。
5. **外部依赖全部可降级**：短信、OSS、内容审核、推送失败不能阻塞主聊天链路。
6. **先做对，再做快**：第一版不做分库分表、不做多机房、不做自研存储。

### 3.3 单体内部的域划分

建议包结构（`com.easychat` 为示例，最终按公司域名定）：

```
com.easychat
├── common          // Result、ErrorCode、异常、枚举、工具、常量
├── infra           // Redis、MyBatis、OSS、SMS、Jackson、线程池、事件总线
├── auth            // 短信、注册、登录、token、设备
├── user            // 账号、资料、设置
├── relation        // 好友、申请、拉黑
├── group           // 群、成员、申请、群事件
├── conversation    // 会话、成员视角、未读/已读
├── message         // 消息、撤回、引用、收藏、同步
├── moment          // 朋友圈、点赞、评论、通知
├── file            // 文件元信息、预签名、回调
├── notification    // 系统通知/角标
├── push            // 移动端离线推送（APNs/厂商通道/EMAS）
├── ws              // Netty 启动、Handler、连接注册、路由
└── admin           // 后台管理（可后置）
```

边界约束（建议用 ArchUnit 测试固化）：
- `moment` 不得直接查 `chat_message`，只能通过 `message` 域接口；
- `ws` 不得直接写业务表，只做协议编解码与投递；
- 所有跨域调用走 Service 接口，不跨域注入 Mapper。

### 3.4 集群方案：从“广播”改成“路由”

v1 是“所有实例订阅一个 Topic，收到后各自看本机有没有这个用户”。节点少时没问题，节点多了每条消息都要广播给所有实例。

v2 建议：

1. 每个 WS 节点启动时生成 `nodeId`，向 Redis 注册：
   `ws:node:{nodeId}`（TTL 30s，心跳续约）。
2. 用户连接成功后写路由：
   `ws:route:{userId}:{deviceId} -> nodeId`（TTL 60s，心跳续约）。
3. 发消息时：
   - 单聊：`MGET` 收件人各设备的 nodeId → 按 nodeId 分组 → 发布到 `ws:node:{nodeId}` 频道；
   - 群聊：维护在线成员集合 `ws:group:{groupId}`，取在线成员 → 按 nodeId 分组 → 每个节点只发一次，携带本节点需要投递的 userId 列表。
4. 节点订阅自己的 `ws:node:{nodeId}`，只推本机连接。
5. 节点宕机：路由 TTL 过期，客户端重连到其他节点；未收到的消息靠 seq 补拉，不依赖推送可靠性。

> 这样消息投递成本从 O(节点数) 降到 O(有收件人的节点数)，是百万在线的前提。

### 3.5 演进路线（微服务拆分点）

| 阶段 | 形态 | 拆分/新增 |
|---|---|---|
| 一 | 模块化单体 | HTTP + WS 同进程；Redis 路由；outbox |
| 二 | 接入与业务分离 | WS 接入集群独立；消息投递服务独立；引入 RocketMQ |
| 三 | 按域拆分 | 用户/关系、群、消息、朋友圈、文件、通知独立服务；MySQL 按 conversation 分片；ES 搜索 |

拆分顺序建议：**WS 接入 → 消息投递 → 朋友圈 Feed → 文件 → 用户/关系**。
不要一上来拆用户服务：用户查询是几乎所有链路的热点，拆早了只会增加 RPC 和缓存不一致。

### 3.6 多端在线与移动推送（Electron + App）

- 连接维度从 `userId` 改为 `userId + deviceId`；`user_device` 记录设备类型、推送 token、最后活跃时间。
- `conversation_member.last_read_seq` 按**用户**共享，不按设备：手机读了，桌面端也同步为已读；每台设备再维护 `last_delivered_seq`（可放 Redis）用于补推。
- Electron：后台常驻 WS、托盘运行；断线指数退避重连；本地 SQLite 缓存消息。
- 移动 App：不能依赖后台长连接。前台的 WS 只负责实时；退到后台后由 APNs/厂商通道推送；用户点开通知后按 `maxSeq` 拉取缺失消息。
- 推送策略：只给**离线设备**推送；同一用户多设备时避免重复通知；支持免打扰、@我、群消息折叠。
- 国内 Android 需要接入华为/小米/OPPO/vivo/荣耀等厂商通道（可用阿里云 EMAS 移动推送聚合）；iOS 用 APNs。

### 4.3 版本落地注意（JDK 21 + Spring Boot 4.1）

**结论：JDK 21 + Spring Boot 4.1.2 可行，但不是“把 v1 的 pom 改个版本号”就能跑。** 下面这些点必须逐项验证：

| 依赖 / 变化 | 处理方式 |
|---|---|
| `spring-boot-starter-web` | Boot 4 已废弃，改用 `spring-boot-starter-webmvc`；旧坐标暂时还能用，但不要新建项目继续用 |
| `spring-boot-starter-test` | 不再自带 MVC 测试；`@WebMvcTest` 要加 `spring-boot-starter-webmvc-test`，包名也变了 |
| MyBatis-Plus | 3.5.13+ 才支持 Boot 4；用 `mybatis-plus-spring-boot4-starter:3.5.18`，不要混入 `mybatis-spring-boot-starter`；分页加 `mybatis-plus-jsqlparser` |
| Redisson | 4.0+ 支持 Boot 4；Boot 4.1 用 4.7.0+ 默认 starter；若是 Boot 4.0，排除 `redisson-spring-data-41`、换 `redisson-spring-data-40` |
| Druid | 1.2.28+ 提供 `druid-spring-boot-4-starter`；但首选 HikariCP，少一个兼容点 |
| Jackson 3 | Boot 4 默认 Jackson 3：`com.fasterxml.jackson` → `tools.jackson`，`ObjectMapper` → `JsonMapper`；第三方库若还依赖 Jackson 2，必须审计 |
| fastjson2 | 能用，但不是默认；Spring MVC 7 下要改用 `HttpMessageConverters.ServerBuilder` 注册，且要开 SafeMode；新代码优先 Jackson 3 |
| Flyway | 只加 `flyway-core` 不会自动迁移；必须 `spring-boot-starter-flyway` + `flyway-mysql` |
| Netty | Boot 4 对齐 Netty 4.2.x；v1 的 Netty 4.1 代码要编译、握手、心跳、断连逐项回归 |
| 图形验证码 | **v2 不采用 EasyCaptcha**；手机号注册统一用短信验证码；异常流量再考虑滑块/云验证码 |
| Sentinel | 1.8.x 对 Boot 4 的 starter 兼容性未确认；先不引入，必要时用 Resilience4j 或自研限流过滤器 |
| RocketMQ | 阶段二再引；Spring Boot starter 可能滞后于 Boot 4，先用原生客户端或等官方适配 |
| Spring AI | 用 **2.0.x**（2.0.0 GA 2026-06），1.1.x 只支持 Boot 3.5 |
| spring-ai-agent-utils | 用 **0.13.x**（基于 Spring AI 2.0.1）；仍是社区孵化项目，API 可能变，放独立模块并锁版本 |

**Flyway 是什么：** 数据库迁移/版本管理工具。把每次表结构变更写成 `V1__init.sql`、`V2__add_index.sql` 这样的 SQL，应用启动时按版本号顺序执行，并在 `flyway_schema_history` 表里记录执行结果和校验和；已执行过的脚本不会重复跑。它解决的是“开发、测试、生产三套库手工改表不一致”的问题，**不是 ORM，也不会替你生成 SQL**。本项目从第一张表开始就由 Flyway 管理，禁止用 `ddl-auto=update` 或手工改生产库。

**落地顺序建议：**

1. 先做一个最小 POC：Boot 4.1.2 + JDK 21 + MySQL + Redis + MyBatis-Plus + Flyway + Netty + springdoc，跑通建表、CRUD、WS 握手和心跳；
2. 再加 Redisson、OSS、Dypnsapi，确认自动配置和线程池没问题；
3. 最后单独加 Spring AI 2.0 + agent-utils 模块，验证 Jackson 3 / Netty 4.2 没有被拉回旧版本；
4. 用 `mvn dependency:tree` 检查是否同时出现 Jackson 2/3、Netty 4.1/4.2；
5. 线上不依赖 SNAPSHOT；父 POM 用 `dependencyManagement` 统一版本；密码用 Jasypt/KMS 加密。

## 5. 数据模型设计

### 5.1 总体原则

1. 表名小写、单数、业务名_作用：`user_account`、`chat_message`、`moment_comment`。
2. 主键 `bigint unsigned`；消息/朋友圈用雪花 ID；对前端输出统一转字符串，避免 JS `Number` 精度丢失。
3. 必备字段：`create_time`、`update_time`；业务删除用 `is_deleted` 或状态位，不物理删除。
4. 索引命名：`pk_`、`uk_`、`idx_`；唯一索引必须建，不能只靠应用层校验。
5. 不用外键、不用级联、不用存储过程。
6. 单表预计 3 年内不超 500 万行/2GB 就不分表；消息表提前确定按 `conversation_id` 分片。
7. 冗余字段只放“不常变、非唯一、非大字段”：如会话最后一条消息摘要、群成员数。
8. 不在数据库存 URL；存 `file_id`/`object_key`，URL 由服务端按权限签发。

| 字段 | 类型 | 说明 |
|---|---|---|

| group_id | bigint | 群 |

#### conversation_member

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | — |
| conversation_id | bigint | 会话 |
| user_id | bigint | 用户 |
| last_read_seq | bigint unsigned | 已读到哪条 |
| last_delivered_seq | bigint unsigned | 已推送到哪条（按用户；设备级可放 Redis） |
| deleted_seq | bigint unsigned | 会话删除水位：`max_seq <= deleted_seq` 时不在列表显示 |
| is_pinned | tinyint | 是否置顶 |
| is_muted | tinyint | 是否免打扰 |
| join_time / update_time | datetime(3) | — |

索引：`uk_conversation_user(conversation_id, user_id)`、`idx_user_conversation(user_id, update_time)`、`idx_conversation_read(conversation_id, last_read_seq)`。
**未读数不落库**：`unread = conversation.max_seq - conversation_member.last_read_seq`。
用户自己发消息时，同步把自己的 `last_read_seq` 推到该消息 seq，避免把“自己发的”算成未读。
**入群/建会话时**：`last_read_seq` 初始化为 `conversation.max_seq`，否则新成员会把入群前的历史消息算成未读，群已读统计也会错。

- `idx_conversation_seq(conversation_id, seq)`

**seq 分配建议**：在同一个事务里

```sql
UPDATE conversation SET max_seq = LAST_INSERT_ID(max_seq + 1) WHERE id = ?;
-- 取 LAST_INSERT_ID() 作为新 seq
INSERT INTO chat_message (..., seq, ...) VALUES (...);
```

优点：连续、有序、持久；同一会话天然串行。缺点：同一会话写有行锁，但会话之间互不影响；单会话超高频场景再评估 Redis 号段。
**不要用时间戳当游标**，也不要只依赖自增 ID 排序。

### 5.4 关键设计决策

#### 决策 1：seq 是会话内序号，不是全局 ID

- `seq` 只在 `conversation_id` 内单调递增，用来排序、补拉、算未读。
- `message.id` 是全局唯一 ID，用来引用、收藏、幂等。
- 客户端只需要保存每个会话的 `maxSeq` 和 `lastReadSeq`，不需要保存“最后下线时间”。

#### 决策 2：未读与已读（单聊 + 群聊都做）

```
未读数 = max(max_seq - last_read_seq, 0)
已读回执 = 成员 last_read_seq >= 我的消息 seq
```

- 单聊：查对方 `conversation_member.last_read_seq`；对方读了就推 `read.receipt` 给我。
- 群聊：
  - 已读人数 = 活跃成员中 `last_read_seq >= message.seq` 的人数；
  - 未读人数 = 活跃成员数 - 已读人数 - 发送者（发送者不计入未读）；
  - 查询按需触发（点开“已读详情”），不要每条消息实时算；
  - 典型 SQL：
    ```sql
    SELECT COUNT(*)
    FROM conversation_member cm
    JOIN group_member gm
      ON gm.group_id = ? AND gm.user_id = cm.user_id AND gm.status = 0
    WHERE cm.conversation_id = ? AND cm.last_read_seq >= ? AND cm.user_id <> ?;
    ```
  - 索引 `idx_conversation_read(conversation_id, last_read_seq)`；500 人群一次 count 扫描量可接受；更大群加 Redis 缓存（5 分钟）或只显示“全部已读/未读”。
  - 群成员入群时 `last_read_seq = conversation.max_seq`，避免历史消息算未读；退群/被踢从统计中排除。
  - 群已读事件只通知**发送者**（聚合后的已读人数），不要广播给全群，避免 N² 写放大。
- 产品建议：单聊消息气泡下显示“已读/未读”；群聊只在我发送的消息上显示“N 人已读”，点开看列表。微信个人版不显示已读，企业微信/QQ 群显示；本项目建议提供“允许关闭已读回执”的用户设置，降低社交压力。

#### 决策 3：撤回 / 删除 / 引用

| 功能 | 方案 |
|---|---|
| 撤回 | `status=1`，清空 `content`（或加密保留审计），记录 `recalled_at/by`；推 `message.recalled`；引用方显示“引用内容已撤回”占位 |
| 双方删除 | 同撤回语义，或 `status=2` 管理员删除；不物理删，保留 seq，避免引用链断裂 |
| 仅删我这边 | 第一版客户端本地删除；要跨端同步再加 `message_hidden` 表 |
| 清空会话 | `conversation_member.deleted_seq = conversation.max_seq`，同时 `last_read_seq = max_seq` 清零未读；新消息到来后 `max_seq > deleted_seq` 自动复活，不需要批量改成员行 |
| 引用 | 存 `quote_message_id` + `quote_snapshot`（发送时的昵称/类型/摘要）；展示时以快照为主，原文撤回/删除时显示占位 |

撤回时限建议 2 分钟（微信规则），群主/管理员“删除他人消息”单独做权限，不要和撤回混用。

#### 决策 4：群成员与会话成员分离

- `group_member` 管“是否在群、角色、群昵称、禁言”；
- `conversation_member` 管“我对这个会话的阅读位置、置顶、免打扰、删除水位”；
- 群成员变化不删 `conversation_member`，保留历史阅读位置；被踢/退群后标记 `group_member.status`，会话可继续只读或从列表移除（产品决定）。

#### 决策 5：朋友圈用拉模式起步

第一版：

```
用户打开朋友圈
→ 取我的好友 ID（缓存）
→ 查这些好友的动态（游标分页）
→ 过滤可见性（全部好友/仅自己/部分可见）
→ 批量补点赞、评论、是否点赞
```

- 优点：发布零扇出，删除/权限变更立即生效；
- 缺点：好友多时查询重。好友上限 5000 时，需要按 `create_time` 游标 + `(user_id, create_time)` 索引，并限制单页 20 条；
- 阶段二：对高活跃用户启用 `moment_feed` 推模式，发布时异步写入活跃好友收件箱；拉模式兜底。

朋友圈不推送“好友发了新动态”，只做“有人点赞/评论我”的通知和红点，和微信一致。

#### 决策 6：收藏是快照，不是引用

收藏一条消息/朋友圈时，把展示所需内容复制进 `favorite.snapshot`，包括文件 `file_id` 和缩略图信息。原消息撤回、原动态删除后，收藏仍然可看。不要只存 `message_id` 去 join，否则历史一删收藏就空。

#### 决策 7：软删除与唯一索引

阿里手册要求逻辑删除，但逻辑删除会破坏唯一索引。统一策略：

- 关系类表（好友、群成员）**不堆积历史行**：一条关系一行，删除改状态，重新建立用 upsert；
- 需要历史轨迹的（申请、操作）单独建日志/申请表，不承担唯一约束；
- 查询条件里带 `status`/`is_deleted`，并在组合索引中前置。

#### 决策 8：ID 与分片

- `user_id`、`message_id`、`moment_id` 用雪花 ID；
- `conversation_id` 用雪花 ID；
- 消息表未来按 `conversation_id` 哈希分片；
- 对外 JSON 一律字符串化 64 位 ID（`"id":"123456789012345678"`），避免前端精度丢失。

### 5.5 数据保留策略（参考微信，按本项目调整）

微信官方帮助中心的口径（2026-11 查询）：

| 数据 | 微信服务器 | 说明 |
|---|---|---|
| 文字消息 | 约 72 小时后从服务器删除 | 已接收的内容主要留在设备本地 |
| 图片/语音/视频/文件 | 发送约 120 小时后从服务器删除 | 未点开的媒体可能更早过期 |
| 未接收的离线消息 | 约 3 天 | 超时后无法再接收 |
| 收藏/群公告 | 长期保留 | 移除收藏后从服务器删除 |
| 朋友圈 | 长期保留，直到用户删除 | — |

> 参考：[微信官方隐私说明](https://cs.help.wechat.com/hc/zh-cn/articles/11975645041807)、[微信消息保留的官方回应](https://m.gmw.cn/2024-08/13/content_1303820100.htm)、[腾讯员工回应微信图片过期](https://m.techweb.com.cn/article/2025-05-16/2960769.shtml)。

> 微信确实支持手机 / 平板 / PC 多端同时在线，但它的“多端”是：**在线设备实时同步 + 各设备本地保存历史 + 换机时做聊天记录迁移**。服务端只做短时中转和近期漫游，不是把所有历史长期存云端。
>
> 所以“照搬微信”技术上可行，但要接受两个体验差异：
> 1. 新设备登录 / 重装后，只能看到服务端保留期内的消息；更早的历史要从旧设备迁移或备份恢复。
> 2. 多端之间的历史一致性依赖“当时在线的设备”，不是随时随地从云端拉全量。

| 档位 | 服务端消息保留 | 媒体保留 | 适用场景 |
|---|---|---|---|
| 微信式（最低成本） | **文字 3 天 / 媒体 5 天**（未接收 3 天） | 文字 3 天、媒体 5 天 | **已拍板，当前采用**；接受新设备看不到旧历史，换机靠迁移 |
| 成本优先（后期可选） | **90 天** | 90 天～1 年 | 用户反馈“换机丢历史”严重时升级 |
| 体验优先（后期可选） | 6 个月热 + 5 年冷 | 6 个月标准 + 归档 | 用户量和收入上来后再升级 |

**已拍板（2026-11-05）：采用微信式。** 服务端只保留文字 3 天、媒体 5 天；已接收内容以客户端本地存储为主；新设备 / 重装只能漫游最近 3 天（媒体 5 天）的消息，更早历史通过旧设备迁移或备份恢复。

> 如果后期用户反馈“换机丢历史”严重，再升级到 90 天或 6 个月 + 归档；表结构不变，只改清理和归档任务的天数配置。

### 当前微信式保留（已拍板）

| 数据 | 服务端保留 | 客户端 | 说明 |
|---|---|---|---|
| 文字消息 | **3 天** | 本地长期 | 新设备 / 重装只能漫游最近 3 天 |

| 头像 | 长期 | — | 只保留当前头像 + 最近 1 个旧版本 |
| 朋友圈 | 长期 | — | 用户主动删除才删 |

| 短信记录 / 敏感操作日志 | 6 个月 | — | 阿里手册 / 合规要求 |

### 备选：体验优先档（后期可选）

| 数据 | 热存储 | 冷存储 | 总保留 | 理由 |
|---|---|---|---|---|
| 聊天消息 | MySQL 6 个月 | 归档库/OSS 5 年 | 5 年（可配置） | 多端漫游、已读、引用、收藏需要 |

## 6. 核心流程

### 6.1 手机号注册 / 登录

```
客户端 → POST /auth/sms/send {phone, scene}
服务端 → 校验手机号格式、IP/手机号/设备限流
       → 调 Dypnsapi SendSmsVerifyCode（CodeLength=6、ValidTime=300、绑定 scene）
       → 记录 sms_record（手机号脱敏、IP、BizId/RequestId、结果）
       → 返回 {expireSeconds, resendAfter}

客户端 → POST /auth/register {phone, code, password?, nickname?, agree}
服务端 → 调 Dypnsapi CheckSmsVerifyCode 校验（校验通过后记录已使用，防重放）
       → 唯一索引插入 user_account；重复手机号走登录或提示
       → 创建 user_profile、user_setting、默认会话/系统通知
       → 签发 accessToken + refreshToken
```

**短信风控**：同手机 60 秒 1 条、1 小时 5 条、1 天 10 条；同 IP 1 小时 20 条；同设备 1 小时 10 条；连续错误 5 次作废；验证码不落日志；虚拟号/黑产号监控。异常流量再触发滑块/云验证码，不默认上图形验证码。
**注意**：阿里云短信签名/模板需要企业资质审核，个人账号可能受限，提前准备。

### 6.2 发送消息（单聊/群聊）

```
客户端 → POST /conversations/{id}/messages
        Header: Idempotency-Key 或 body.clientMsgId
服务端（一个事务）→
  1. 校验：登录态、会话成员、好友/群状态、禁言、消息类型/大小、限流
  2. UPDATE conversation SET max_seq = LAST_INSERT_ID(max_seq+1)
  3. INSERT chat_message（seq、client_msg_id 唯一）
  4. UPDATE conversation 的最后消息摘要
  5. UPDATE 发送者 conversation_member.last_read_seq = seq
  6. INSERT event_outbox（message.created）
  7. 返回 {messageId, seq, sendTime}
事务提交后 → outbox relay
  → 查收件人在线路由 → 按 node 投递 → WS 推 msg.new
  → 离线/失败不重试推送，靠客户端 seq 补拉
```

要点：
- 媒体消息**先上传 OSS 拿 fileId，再发消息**，不要先造“发送中”消息；
- `clientMsgId` 唯一索引兜底重试，重复请求直接返回原消息；
- 发送者自己的 `last_read_seq` 要推进，否则未读数会把自己发的也算进去。

### 6.3 重连与离线同步

```
WS 建连（ticket 校验通过）
服务端 → S2C init {
  conversations: [{id, type, maxSeq, lastReadSeq, lastMessage, unread}],
  friendApplyCount, groupApplyCount, momentUnread
}
客户端 → 对当前打开的会话 GET /conversations/{id}/messages?afterSeq={localMaxSeq}
       → 用 seq 去重、补洞
```

**不再**在 INIT 里塞全量离线消息；会话列表只带摘要和游标。这样离线 30 天也不会把首包撑爆。

### 6.4 已读上报（单聊 + 群聊）

```
客户端打开会话/滚到底部
→ POST /conversations/{id}/read {seq}
服务端 → last_read_seq = GREATEST(last_read_seq, seq)
       → 单聊：推 read.receipt 给对方
       → 群聊：只给发送者推聚合后的已读人数（若发送者在线），不广播全群
       → 本用户其他设备也推 read.receipt，保证多端同步
       → 未读数由 max_seq - last_read_seq 实时算出
```

群聊“点开看具体成员”：

```
GET /messages/{messageId}/read-receipt?cursor=&limit=50
→ 校验当前用户是该消息发送者（默认）；群主/管理员是否可见可配置
→ 返回 readCount、unreadCount、readers[]（分页）
→ readers 只包含开启了已读回执、且 last_read_seq >= message.seq 的活跃群成员
→ 关闭已读回执的用户不计入 readers，也不计入已读/未读统计分母；前端只展示愿意共享的成员
→ 大群分页返回，计数结果可缓存 30～60 秒
```

### 6.5 撤回

```
发送者 → POST /messages/{id}/recall
服务端 → 校验发送者、会话成员、status=0、2 分钟内、未过期
       → UPDATE status=1, content=NULL, recalled_at, recalled_by
       → 若它是会话最后一条，更新 last_message_preview='[消息已撤回]'
       → outbox: message.recalled
客户端 → 把对应消息替换为“已撤回”占位；引用该消息的气泡显示“引用内容已撤回”
```

### 6.6 朋友圈发布与查看

```
发布：POST /moments {content, media:[fileId], visibility, audience[]}
→ 校验文件归属/审核状态
→ INSERT moment + moment_media + moment_audience
→ 不扇出到好友收件箱

查看：GET /moments/feed?cursor=...
→ 取好友 ID（缓存）

→ 批量查点赞/评论、当前用户是否点赞
```

## 7. API 与 WebSocket 协议

### 7.1 REST 约定

- 前缀 `/api/v1`；资源用复数；动作用子资源：`POST /messages/{id}/recall`。
- 响应统一：

```json
{ "code": "0", "message": "ok", "data": {}, "traceId": "..." }
```

- 错误码按阿里手册：`A0xxx` 用户端、`B0xxx` 系统端、`C0xxx` 第三方；业务细分码放 `data.bizCode`。
- 列表分页：消息/动态用 `cursor + limit`，后台管理可用 `pageNo + pageSize`。
- 幂等：发消息用 `clientMsgId`；其他写接口用 `Idempotency-Key` 请求头。
- 时间：接口统一返回 epoch 毫秒（`long`）或 ISO-8601 带时区，二选一；数据库用 `datetime(3)`。
- ID：64 位整数一律输出字符串。

### 7.2 核心接口清单（粗粒度）

| 域 | 接口 |
|---|---|
| 认证 | `POST /auth/sms/send`、`POST /auth/register`、`POST /auth/login`、`POST /auth/refresh`、`POST /auth/logout`、`POST /auth/ws-ticket` |
| 用户 | `GET /users/me`、`PUT /users/me`、`PUT /users/me/password`、`GET /users/{id}` |
| 好友 | `GET /contacts`、`GET /contacts/search`、`POST /contacts/apply`、`GET /contacts/applies`、`POST /contacts/applies/{id}/handle`、`DELETE /contacts/{id}`、`POST /contacts/{id}/block` |
| 群 | `POST /groups`、`GET /groups`、`GET /groups/{id}`、`PUT /groups/{id}`、`DELETE /groups/{id}`、`POST /groups/{id}/members`、`DELETE /groups/{id}/members/{uid}`、`POST /groups/{id}/leave`、`GET /groups/{id}/applies` |
| 会话 | `GET /conversations`、`DELETE /conversations/{id}`、`POST /conversations/{id}/read`、`PUT /conversations/{id}/settings` |
| 消息 | `POST /conversations/{id}/messages`、`GET /conversations/{id}/messages?beforeSeq/afterSeq`、`POST /messages/{id}/recall`、`POST /messages/{id}/hide`、`GET /messages/{id}/read-receipt?cursor=&limit=` |
| 朋友圈 | `POST /moments`、`GET /moments/feed`、`GET /moments/{id}`、`DELETE /moments/{id}`、`POST /moments/{id}/like`、`DELETE /moments/{id}/like`、`POST /moments/{id}/comments`、`DELETE /moments/comments/{id}` |
| 收藏 | `POST /favorites`、`GET /favorites`、`DELETE /favorites/{id}` |
| 文件 | `POST /files/presign`、`POST /files/{id}/complete`、`GET /files/{id}/url` |

### 7.3 WebSocket 事件

统一帧：

```json
{ "v": 1, "type": "msg.new", "eventId": "evt_...", "ts": 1730000000000, "data": {} }
```

| 方向 | type | 说明 |
|---|---|---|
| C→S | `ping` | 心跳（也可用 WS Ping/Pong） |
| C→S | `ack` | 确认收到某个 seq（可选） |
| C→S | `read` | 已读上报（也可走 HTTP） |
| C→S | `typing` | 正在输入（内部限流，不落库） |
| S→C | `init` | 连接初始化：会话列表 + 游标 + 各类未读数 |
| S→C | `msg.new` | 新消息 |
| S→C | `msg.recalled` | 撤回 |
| S→C | `msg.deleted` | 管理员删除/双方删除 |
| S→C | `conv.update` | 会话摘要/未读/置顶变化 |
| S→C | `read.receipt` | 已读回执：单聊推给对方；群聊只推给发送者聚合已读人数 |
| S→C | `friend.apply`、`group.event` | 申请/群事件 |
| S→C | `moment.notify` | 点赞/评论通知 |
| S→C | `force.logout` | 强制下线 |
| S→C | `error` | 协议/业务错误 |

规则：
- 消息至少一次投递；客户端按 `messageId` 去重，按 `seq` 排序，发现缺号主动补拉；
- 重连指数退避 + 抖动（1s、2s、4s、8s……上限 30s），不要固定 5 秒；
- 心跳 20～30 秒；服务端 90 秒无活动断开；在线状态 TTL 60 秒，避免网络抖动误判；
- 慢客户端：`channel.isWritable()` 检查，写缓冲超过高水位丢弃可丢事件（typing/presence），严重时断开；
- 消息体上限 64KB；超长文本走文件/分片，不在 WS 里传大 JSON。

## 8. 文件：OSS + CDN

### 8.1 上传（直传，不经应用服务器）

```
1. 客户端 POST /files/presign
   { bizType, fileName, size, contentType, sha256 }
2. 服务端校验：登录、配额、类型白名单、大小、bizType 权限
   → 生成 objectKey：{biz}/{yyyy}/{MM}/{uuid}.{ext}
   → INSERT file_info(status=0)
   → 返回 { fileId, uploadUrl, method, headers, expireAt }
3. 客户端 PUT 文件到 OSS 预签名 URL（大文件用分片上传）
4. OSS 回调 /files/callback（验签）或客户端 POST /files/{id}/complete
   → 服务端 HEAD 校验 size/content-type
   → status=1
5. 发消息/发朋友圈时带 fileId
```

- 预签名 URL 的 policy 必须限制：bucket、key 前缀、Content-Type、大小；
- 不要把 AccessKey 下发到客户端；用 STS 临时凭证或服务端签名；
- 上传失败/超时：`file_info` 停留 status=0，定时任务 24 小时后清理孤儿对象。

### 8.2 读取（CDN + 签名）

| 类型 | 策略 |
|---|---|
| 头像/公开图 | 公开读或 CDN 防盗链，长缓存 |
| 聊天图片/视频/文件 | 私有，服务端鉴权后签发 CDN 签名 URL（10～30 分钟） |
| 朋友圈图片/视频 | 私有，签名 URL；缩略图走 OSS 图片处理 |
| 收藏快照 | 与源文件同策略，签名 URL |

注意：签名 URL 每次变化会降低 CDN 缓存命中率。折中：
- 对象 key 用不可猜测的 UUID；
- 对图片使用较长 TTL（如 1 小时）+ CDN 鉴权，避免每次刷新都回源；
- 高敏感文件（合同/证件）用短 TTL + 不回源缓存。

### 8.3 OSS 目录与生命周期

```
avatar/{userId}/{uuid}.{ext}          // 公开
chat/{yyyy}/{MM}/{uuid}.{ext}         // 私有
moment/{yyyy}/{MM}/{uuid}.{ext}       // 私有
favorite/{yyyy}/{MM}/{uuid}.{ext}     // 私有
temp/{yyyy}/{MM}/{uuid}               // 1 天生命周期
```

- 图片统一 `x-oss-process=image/resize,w_400/format,webp/quality,q_80` 生成列表缩略图；
- 视频封面：客户端上传封面（v1 做法）或 OSS 媒体处理截帧；
- 开启版本控制/跨区域复制（按预算）；开启服务端加密；
- 生命周期：temp 1 天；聊天媒体标准 6 个月 → 低频 18 个月 → 归档至 5 年；朋友圈长期（1 年后转低频）；用户注销后按合规要求删除/匿名化。

### 8.4 内容安全

- 文本：敏感词 + 阿里云内容安全；
- 图片/视频：异步审核；头像/朋友圈审核通过才展示；
- 聊天图片：可先发后审，命中违规时撤回并通知；
- 审核回调幂等，失败重试；审核服务降级时不能阻塞发送（标记 pending）。

## 9. 短信、账号与安全

### 9.0 短信服务：阿里云 Dypnsapi（个人可用）

- 使用**号码认证服务 Dypnsapi（2017-05-25）**，不是传统短信服务 Dysmsapi：
  - `SendSmsVerifyCode`：发送短信验证码（可指定签名、模板、长度、有效期、重发间隔）；
  - `CheckSmsVerifyCode`：校验手机号 + 验证码。
- 个人实名账号可开通“短信认证”，服务自带签名/模板；传统 Dysmsapi 需要企业资质报备签名，个人不适合。
- 代码层面抽象 `SmsSender` 接口，`DypnsapiSmsSender` 实现；将来换企业短信/其他供应商只换实现，不影响业务。
- 个人版可能有发送号码白名单、条数上限、模板限制（网上有“5 个号码”的反馈，需以控制台为准）；上线商用前确认配额、资费和条款。
- 移动 App 可额外接入一键登录（`GetMobile`/`GetPhoneWithToken`），Electron/Web 继续用短信验证码。
- 风控仍以本地为准：手机号/IP/设备限流、图形验证、场景隔离；Dypnsapi 校验通过后用 Redis 记录已使用，防止重放。
- 参考：[SendSmsVerifyCode](https://next.api.alibabacloud.com/api/Dypnsapi/2017-05-25/SendSmsVerifyCode)、[Dypnsapi CLI 中心](https://troubleshooting.api.aliyun.com/api-tools/cli/Dypnsapi/2017-05-25)。

### 9.1 认证

- accessToken：JWT，2 小时；refreshToken：不透明随机串，30 天，存 Redis，可撤销；
- 刷新时轮换 refreshToken；改密/注销/踢设备时撤销全部会话；
- 密码：BCrypt（cost 10～12），禁止 MD5/SHA1；
- WS：先用 accessToken 换一次性 `wsTicket`（30 秒、一次性），再建连，避免 token 进 URL 日志。

### 9.2 授权

每个对象操作都要校验：
- 会话消息：当前用户是否 `conversation_member`；
- 群操作：是否群成员/管理员/群主；
- 文件签名：是否上传者、消息参与者、朋友圈可见者；
- 收藏：是否本人；
- 朋友圈评论/点赞：是否可见该动态。

不要相信客户端传来的 `userId`、`conversationId`、`fileId` 归属。

### 9.3 限流与防刷

| 场景 | 限制 |
|---|---|
| 短信发送 | 手机 60s/条、5 条/小时、10 条/天；IP 20 条/小时；先过图形/滑块 |
| 登录/注册 | IP + 手机号 + 设备维度；连续失败锁定 |
| 发消息 | 用户每秒 N 条、每分钟 N 条；群发更严 |
| 加好友/入群 | 每天上限；被拒绝冷却 |
| 朋友圈发布 | 每天上限；媒体数量/大小 |
| 文件预签名 | 用户配额、并发数、大小 |

工具：Redis + Lua 滑动窗口；接口级 Sentinel 限流；网关层兜底。

### 9.4 日志与隐私

- 手机号、token、验证码、密码、身份证等脱敏；
- 敏感操作日志保留 6 个月（阿里手册要求）；
- 不在日志里打印完整消息内容（尤其群聊）；
- 用户注销：软删账号 + 匿名化展示 + 按合规保留必要日志，清理 OSS 个人文件；
- 隐私政策、用户协议、个人信息收集清单、未成年人保护；国内上线需 ICP 备案、公安备案，IM 业务关注实名与内容安全要求。

## 10. 部署与运维

### 10.1 部署拓扑（当前单机 / 扩容后）

扩容后的推荐拓扑：

```
SLB（HTTPS/WSS）
  ├── ECS 8C4G × 2（应用：Spring Boot + Netty，JVM 2.5～3G，双活/高可用）
  ├── 云 RDS MySQL 8.0（2C4G 起，主从/备份）
  ├── 云 Redis 7（2G 起，主从）
  ├── OSS + CDN
  ├── 阿里云 Dypnsapi 短信
  └── 内容安全 / EMAS 移动推送
```

当前预算的 1～2 千在线拓扑（已选 4C8G 全栈）：

```
ECS 4C8G × 1（jar + MySQL + Redis 同机）
  ├── JVM 3G（堆 2.5G + 直接内存 512M）
  ├── MySQL 1.5～2G（buffer pool 1～1.5G，ESSD 100～200G）
  ├── Redis 512M～1G（maxmemory 512M，allkeys-lru）
  └── OS / 页缓存 1.5～2G
带宽 10～20Mbps；文件走 OSS，不占应用带宽
```

> 4C8G 全栈是单点：必须做每日快照 + binlog 备份到 OSS；MySQL 和 Redis 要设内存上限，避免把系统内存打满。后续增长优先把 MySQL 拆到云 RDS。

成本优先的 1～2 万在线单机拓扑（后续升级）：

```
ECS 8C16G（应用 + MySQL + Redis 同机）
  ├── JVM 6～7G（堆 + 直接内存）
  ├── MySQL 3～4G（buffer pool 2～3G，ESSD 200～500G）
  ├── Redis 1～2G（maxmemory 1G，allkeys-lru）
  └── 系统 / 页缓存 2～3G
带宽 20～50Mbps；文件走 OSS，不占应用带宽
```

不要把 MySQL、Redis 和 4G 的应用挤在一台机器上。预算紧张时，应用选 **4C8G** 比 8C4G 更合理；生产建议至少 2 个应用节点。**单机 8C16G 只适合早期 1～2 万在线，必须配快照、备份和监控；它是单点故障，宕机即全站不可用。**

### 10.2 操作系统与 JVM

Linux 参数建议：

```
ulimit -n 1048576
fs.file-max = 2097152
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535
net.ipv4.ip_local_port_range = 1024 65000
net.ipv4.tcp_fin_timeout = 30
net.ipv4.tcp_tw_reuse = 1
net.core.netdev_max_backlog = 65535
```

JVM 建议（JDK 21，8C4G 只跑应用）：

```
-Xms2560m -Xmx2560m
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump
-XX:MaxDirectMemorySize=768m
-XX:+UseG1GC
-XX:+ExitOnOutOfMemoryError
-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags
```

JVM 建议（JDK 21，4C8G 全栈：jar + MySQL + Redis）：

```
-Xms2560m -Xmx2560m
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump
-XX:MaxDirectMemorySize=512m
-XX:+UseG1GC
-XX:+ExitOnOutOfMemoryError
-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags
```

8C16G 只跑应用时，可按 8G 堆 + 2G 直接内存；如果 MySQL/Redis 同机，JVM 降到 6～7G（含直接内存），给数据库和页缓存留空间。4C8G 全栈时 MySQL `innodb_buffer_pool_size` 控制在 1～1.5G，Redis `maxmemory` 控制在 512M，不要把堆和直接内存加起来顶满物理内存。

Netty：Linux 用 Epoll；`SO_BACKLOG`、`TCP_NODELAY`；`IdleStateHandler` 做心跳；写缓冲水位防慢客户端；不要在 EventLoop 里做阻塞 IO/DB。

Nginx/SLB：WebSocket 需要 `proxy_read_timeout` 调大（如 3600s）、`proxy_buffering off`、保持 Upgrade/Connection 头。

### 10.3 监控与告警

| 指标 | 说明 |
|---|---|
| WS 连接数、建连/断连速率 | 容量与异常抖动 |
| 消息发送 TPS、推送延迟 P99 | 核心链路 |
| HTTP P99、错误率、限流次数 | 接口健康 |
| MySQL 连接数、慢查询、主从延迟 | 存储 |
| Redis 命中率、延迟、内存、evict | 缓存 |
| JVM GC 暂停、堆/直接内存 | 稳定性 |
| OSS/CDN 上传下载失败率 | 弱依赖 |
| 短信发送成功率/失败码 | 注册转化 |

告警：连接数突降、消息积压、DB 主从延迟、Redis evict、错误率 > 阈值。
日志：JSON 结构化 + `traceId` + `userId`（脱敏）；SLS/ELK；保留策略按合规。

### 10.4 备份与容灾

- RDS 自动备份 + binlog，定期恢复演练；
- Redis 开启 AOF/RDB（云托管自动）；会话/路由丢失可重建，消息不可丢；
- OSS 版本控制 + 生命周期；
- 配置/密钥备份到 KMS/密钥管理；
- 单节点故障：SLB 摘除 + 客户端重连 + seq 补拉；
- 数据库故障切换：RDS 主从自动切换，应用重连；
- 演练：杀节点、Redis 主从切换、RDS 切换、OSS 限流。

### 10.5 CI/CD

- `mvn verify`：编译、单测、ArchUnit、Checkstyle/SpotBugs（可选）；
- Flyway 迁移随版本发布，禁止手工改生产库；
- Docker 镜像（eclipse-temurin:21-jre），滚动/蓝绿发布；
- 配置用环境变量/KMS，不打包进镜像；
- 发布前跑冒烟：登录、建会话、发消息、WS 收消息、上传下载。

```
└── docs/
```

- 后续拆微服务时，域包直接升级为模块；
- 用 ArchUnit 测试禁止跨域直接访问 Mapper；
- 不建“大而全”的 utils，公共能力按职责拆。

### 12.2 分层

`Controller`（参数校验/协议转换）→ `Service`（业务编排/事务）→ `Manager`（缓存、第三方、通用能力）→ `Mapper`（数据访问）。

- Controller 不写业务、不直接调 Mapper；
- Service 不返回 DO，返回 DTO/VO；
- 外部调用（OSS/SMS）放 Manager，必须设置超时；
- DAO 异常统一包装，Service 记录上下文日志。

### 12.3 命名与模型

- 包名 `com.easychat.xxx`；类名 `XxxController/Service/Manager/Mapper`；
- DO（数据库映射）、DTO（传输）、VO（展示）、Query（查询参数）；
- 枚举属性 `private final`，提供 `getByCode`；
- 禁止魔法值，常量集中定义；
- 接口/方法参数超过 2 个用 Query/DTO 封装，不用 Map。

### 12.4 异常与错误码

- `BusinessException(ErrorCode)`；全局 `@RestControllerAdvice` 统一处理；
- 错误码按 `A/B/C` 分类，前端按 code 处理；
- 不吞异常；不 `catch(Exception e) {}`；
- 日志带 `traceId`、用户 ID（脱敏）、关键业务 ID；
- 对外不暴露堆栈/SQL。

### 12.5 事务与并发

- `@Transactional(rollbackFor = Exception.class)` 只加在 Service；
- 事务内不调用 OSS/SMS/HTTP；先提交再发事件（outbox）；
- 事务尽量短，避免大事务锁表；
- 分布式锁用 Redisson，必须设置 lease/看门狗；能不用锁用唯一索引/乐观锁；
- 计数用 `UPDATE ... SET count = count + 1`，不要先查后写；
- 避免在 EventLoop/定时任务里做长耗时操作，用独立线程池。

### 12.6 MySQL

- 查询列明确写，禁止 `SELECT *`；
- 禁止超过 3 表 join；关联字段类型一致且有索引；
- 禁止左模糊/全模糊；搜索走搜索引擎；
- 深分页用游标/延迟关联；
- 唯一业务字段必须建唯一索引；
- 批量 insert 控制批次（500～1000）；
- 不用外键、存储过程、触发器；
- 字段非负用 unsigned；小数用 decimal；
- 索引命名 `pk_/uk_/idx_`；
- 变更走 Flyway，生产前 double check。

### 12.7 单元测试

- 核心域（seq、未读、撤回、权限、朋友圈可见性）必须有单测；
- 测试命名 `方法_场景_预期`；
- 不依赖真实网络/生产数据；
- 集成测试用 Testcontainers；
- 覆盖率不追求数字，优先覆盖边界和状态转换。

**当前优先做 M1～M3 的 IM 基础功能**：注册登录、好友、单聊、群聊、文件、离线补拉、未读数。撤回/删除/引用、已读回执、好友备注修改、朋友圈、审核、三天可见、收藏、EMAS 都放到 M4 之后，不阻塞主流程。

## 15. 风险清单（Top 14）

1. **把“百万并发”当第一版目标** → 过度设计、交付延期。先做可验证的 1～2 千在线，再按 5～10 万扩容压测。
2. **消息表没有 seq/分片键** → 后期无法平滑扩展，只能停服迁移。
3. **未读数前端维护** → 多端不一致、红点复活；必须服务端化。
4. **WS 全局广播** → 节点一多就成倍放大；必须路由表。
5. **文件走应用服务器** → 带宽打满、扩容困难；必须直传 OSS。
6. **事务内调用第三方** → 长事务、连接池耗尽；外部调用移出事务。
7. **没有幂等** → 重试产生重复消息/重复好友申请/重复点赞。
8. **没有内容审核** → 合规风险，可能被下架。
9. **配置明文密钥** → 安全事故；用 KMS/Jasypt。
10. **一开始微服务化** → 小团队运维成本爆炸，核心功能反而做不完。
11. **移动端只靠 WS** → App 切后台连接被系统杀掉，消息收不到；必须接厂商推送 + 点开补拉。
12. **个人短信服务配额/号码限制** → 注册量上来后发不出验证码；上线前确认 Dypnsapi 配额和商用条款。
13. **单机 8C16G 全栈 = 单点故障** → 机器宕机、MySQL 损坏就是全站不可用；必须做每日快照 + binlog 备份到 OSS，并提前准备“应用迁到第二台机器、数据库用云 RDS”的逃生方案。
14. **微信式 3/5 天保留导致新设备看不到旧历史** → 用户会认为“聊天记录丢了”；客户端必须提供本地备份/换机迁移，产品上要明确说明服务端只保留最近 3 天。

## 附：与微信做法的对照

| 能力 | 微信做法 | 本项目建议 |
|---|---|---|
| 单聊已读 | 个人微信不显示已读 | 产品可选；技术上用 `last_read_seq` |

| 引用 | 引用消息 + 原文撤回显示占位 | `quote_message_id + snapshot` |

| 文件 | 图片/视频 CDN、文件直传 | OSS + CDN 签名 |
| 注册 | 手机号 + 验证码 | 阿里云短信 + 风控 |
