# 表结构说明（V1 基础 IM）

> DDL 以 Flyway 脚本为准：[V1__init_schema.sql](../src/main/resources/db/migration/V1__init_schema.sql)
> 数据库：MySQL 8.0 / InnoDB / utf8mb4

## 1. V1 范围

第一阶段只建 IM 基础功能需要的表：

- 手机号注册登录、用户资料、设置、多端设备；
- 好友、好友申请、黑名单；
- 群、群成员、入群申请；
- 会话、会话成员、消息、@提醒、事件发件箱；
- 文件元信息、短信发送记录。

**暂不建**：朋友圈、收藏、消息撤回/引用扩展字段、群已读详情、EMAS 推送记录。后续用 V2、V3… 增量迁移。

## 3. 关键设计

### 3.1 ID

- `user_id`、`conversation_id`、`chat_message.id`、`file_info.id`、`group_info.id` 使用雪花 ID；
- 对前端 JSON 输出时统一转字符串，避免 JavaScript 精度丢失；
- 关系表、日志表、outbox、短信记录使用自增 `id`，业务唯一性靠唯一索引约束。

**为什么不全部用雪花：**

- 关系/日志表是内部数据，不对外暴露，自增主键更小、顺序写入更好，B+ 树更紧凑；
- 雪花 ID 依赖 `workerId` 和时钟，多节点部署要额外处理；当前 1 台 4C8G 没必要把所有表都上雪花；
- 对外实体和未来可能按会话分片的表用雪花，兼顾唯一性和扩展性。后期真要全量分片，再统一迁移。

**雪花 ID 落地注意：**

- 单机可以固定 `workerId=1`；集群用 Redis/数据库统一分配，不要用 MAC/PID 推导（容器里容易撞）；
- 服务器开 NTP；代码要处理时钟回拨；
- 雪花值小于 `Long.MAX_VALUE`，Java 用 `Long` 没问题；MySQL `BIGINT UNSIGNED` 也能正常 `getLong`，但要实际验证驱动映射；
- API 返回 ID 一律字符串，前端不要用 `Number` 接。

### 3.2 会话内 seq

- `conversation.max_seq` 是会话内单调递增序号；
- 发消息时在同一事务内分配 `seq`：

```sql
UPDATE conversation SET max_seq = LAST_INSERT_ID(max_seq + 1) WHERE id = ?;
INSERT INTO chat_message (..., seq, ...) VALUES (...);
```

- 离线补拉、排序、未读、已读都以 `seq` 为游标，不用时间戳。

### 3.3 未读数

```text
未读数 = max(conversation.max_seq - conversation_member.last_read_seq, 0)
```

- 不单独存未读数字段，避免多端不一致；
- 用户自己发消息时，同步推进自己的 `last_read_seq`；
- 清空会话：`deleted_seq = max_seq`，同时 `last_read_seq = max_seq`。

### 3.4 好友关系

- `user_friend` 一条好友关系存两行：A→B、B→A；
- 删除好友把两行 `status` 改为 1，重新加好友时 upsert 回 0；
- 拉黑单独放 `user_blacklist`，不要和好友状态混在一起。

### 3.5 群成员与会话成员分离

- `group_member` 管“是否在群、角色、群昵称、禁言”；
- `conversation_member` 管“读到哪、置顶、免打扰、删除水位”；
- 退群/被踢只改 `group_member.status`，保留 `conversation_member` 的历史阅读位置。

### 3.6 消息幂等

- 客户端生成 `client_msg_id`；
- `uk_sender_client(sender_id, client_msg_id)` 兜底重复发送；
- 重试命中唯一索引时，返回原消息，不重复插入。

### 3.7 文件

- 数据库只存 `bucket`、`object_key`、元信息，不存公开 URL；
- 客户端先上传 OSS，再拿 `file_id` 发消息；
- 读取时由服务端签发 CDN 签名 URL，并校验会话/朋友圈权限。

## 5. Flyway 规则

- 文件名：`V1__init_schema.sql`、`V2__xxx.sql`，版本号递增；
- 已执行的脚本不要修改，改表新增版本；
- 不使用 `ddl-auto=update`，生产库不手工改表；
- 生产执行前先在测试库跑一遍；
- 大表 DDL 评估锁表时间，必要时用 online DDL 或分批迁移。

## 6. 表结构设计详解（为什么这么设计）

### 6.1 全局约定及理由

V1 脚本头部四条约定，每条都有明确动机：

| 约定 | 为什么 |
|---|---|
| 不使用外键、触发器、存储过程 | 外键级联是强阻塞操作，高并发下引发"更新风暴"和死锁（阿里规约【强制】禁止）。关联完整性由应用层保证，但关联字段上照样建索引 |
| 内容表 `is_deleted` / 关系表 `status` 逻辑删除 | 删好友、退群、撤回都要可追溯、可恢复；关系是"状态可逆"的（status 0/1 切换），内容删除走 `is_deleted` |
| 时间统一 `datetime(3)` | IM 消息排序精度到毫秒，`datetime` 默认只到秒，同一秒内两条消息分不出先后 |
| 对外实体用雪花 ID，内部辅助表用自增 | 用户/会话/消息/文件的 ID 对外暴露，自增会被猜测遍历且分库分表后冲突；成员/申请/记录类表是内部数据，自增主键更小、顺序写入 B+ 树更紧凑（详见 3.1） |

每张表都有 `id / create_time / update_time` 三件套（阿里规约【强制】）。

### 6.2 账号域（4 张）

**user_account**

- `uk_country_phone (country_code, phone)`：手机号只在「区号+号码」范围内唯一，`+86` 和 `+1` 的同号是两个人，必须联合唯一索引。阿里规约【强制】业务唯一字段必须建唯一索引兜底——并发下应用层校验必然有漏网；
- `idx_status_create (status, create_time)`：后台查"某状态用户按注册时间排"，等值列在前、排序列在后，避免 filesort。

**user_profile / user_setting**：与账号一对一拆表。账号表（登录热行）和资料表（展示字段多）读写特征不同，拆开避免"改签名也锁账号行"；setting 单独拆是因为开关类字段会持续增长。

**user_device**

- `uk_user_device (user_id, device_id)`：同用户同设备只允许一行，重复登录走 UPDATE，防止推送表膨胀；
- `idx_user_active (user_id, last_active_time)`：发推送查"用户最近活跃的设备"，等值 + 排序正好走索引序。

### 6.3 好友域（3 张）

**user_friend（双向两行）**

- A 加 B 存 `(A,B)` 和 `(B,A)` 两行，"我的好友列表"只按 `user_id` 扫，不用 OR；
- `uk_user_friend (user_id, friend_user_id)`：防重复加好友；
- `idx_friend_user (friend_user_id, status)`：反查"谁把我当好友"（删号清理）、校验对方是否已解除关系。同一组列建两种顺序的索引，因为组合索引只服务最左前缀，两个查询方向就需要两个索引。

**friend_apply**

- `idx_receive_status (receive_user_id, status, create_time)`：最高频查询"我收到的待处理申请"：`WHERE receive_user_id = ? AND status = 0 ORDER BY create_time DESC`，等值、等值、排序——组合索引列顺序的标准模板；
- `idx_apply_user (apply_user_id, create_time)`：反方向"我发出的申请"。

**user_blacklist**

- `uk_user_blocked (user_id, blocked_user_id)`：拉黑幂等，重复拉黑撞唯一键而不是插两行；该索引同时是发消息前校验 `WHERE user_id = ? AND blocked_user_id = ?` 的查询索引，不重复建。

### 6.4 群域（3 张）

**group_info**：`uk_group_no`（群号对外可搜，必须唯一）、`idx_owner`（查我创建的群）。

**group_member —— 组合索引经典案例**

```sql
UNIQUE KEY uk_group_user (group_id, user_id)   -- 群内成员唯一
KEY idx_user_status (user_id, status)           -- "我加入了哪些群"
KEY idx_group_status (group_id, status)         -- "群成员列表"
```

- 看群成员列表 → 先按 `group_id` 定位 → `idx_group_status`；
- 用户侧边栏展示我的群 → 先按 `user_id` 定位 → `idx_user_status`；
- 只建其中一个，另一方向退化为大范围扫描。`status` 放第二位让索引内直接过滤已退群/被踢的行。

**group_apply**：与 friend_apply 同构，`idx_group_status` 服务群主看申请，`idx_apply_user` 服务申请人看进度。

### 6.5 会话与消息域（4 张）—— IM 核心

**conversation**

- 单聊+群聊一张表，`type` 区分。单聊唯一键 `single_key = minUserId:maxUserId`（两 ID 排序后拼接），A 聊 B 与 B 聊 A 天然是同一会话，建会话时自动去重；
- `uk_group_id`：`group_id` 为 NULL 的单聊行不冲突——MySQL 唯一索引允许多个 NULL，唯一约束只对群聊会话生效，正好是想要的语义；
- `max_seq / last_message_*` 是冗余字段（阿里规约【推荐】：冗余换性能）：会话列表要显示最后一条消息，不冗余就得逐会话回查消息表。

**conversation_member —— 消息全局一份，每人一份游标**

```text
last_read_seq       已读水位      → 未读数 = max_seq - last_read_seq
last_delivered_seq  已推送水位    → 离线补拉 = seq > last_delivered_seq 的消息
deleted_seq         删除会话水位  → 清空会话后不再拉旧消息
```

未读数、补拉都是纯数字比较，不扫消息表。

- `idx_user_update (user_id, update_time)`：拉用户会话列表，按最近活跃排序；
- `idx_conversation_read (conversation_id, last_read_seq)`：群已读详情（谁读到了哪条）。

**chat_message —— 每个索引对应一条真实查询路径**

```sql
UNIQUE KEY uk_conversation_seq (conversation_id, seq)   -- ①
UNIQUE KEY uk_sender_client (sender_id, client_msg_id)  -- ②
KEY idx_conversation_time (conversation_id, send_time)  -- ③
KEY idx_sender_time (sender_id, send_time)              -- ④
```

- ① 核心中的核心。`seq` 由服务端在发消息事务内分配（见 3.2），联合唯一索引一石三鸟：保证会话内消息顺序；并发抢同一 seq 只有一个成功，顺序绝不乱；离线补拉 `WHERE conversation_id = ? AND seq > ? ORDER BY seq LIMIT 50` 范围扫 + 排序全是索引序，零 filesort；
- ② 客户端幂等（见 3.6）。弱网重发同一 `client_msg_id` 只落库一条。联合键带 `sender_id` 而不是单列，避免不同用户的本地 ID 撞车；
- ③ 按时间翻历史消息的场景；
- ④ "我发过的消息"、发送频率风控；
- ①③ 并存的原因：一个索引只有一种排序，seq 游标和时间游标两种协议就要两个索引。`content JSON` 放行尾，让前面的列紧凑、索引页容纳更多行。

**message_mention**：`uk_message_user`（一条消息@同一人只记一次）、`idx_user_create`（"@我的消息"通知页）。

**event_outbox —— 本地事务 + 异步投递**

- 写消息与写事件同事务落库，异步线程投递下游（推送/未读/审核），保证"消息存了但推送丢了"不会发生；
- `idx_status_next (status, next_retry_time)`：扫描器跑 `WHERE status IN (0,2) AND next_retry_time <= now ORDER BY next_retry_time`，等值在前、范围排序在后。

### 6.6 文件与短信（2 张）

**file_info**

- `uk_object_key`：OSS object key 唯一，防重复上传覆盖同路径；
- `idx_uploader_create`：查"我上传过的文件"；
- `sha256` 预留秒传/去重：同 hash 不必再传 OSS；
- 状态 `0上传中`：先建记录拿 `file_id` 再分片上传，中间态落库不落内存。

**sms_record —— 三个索引全是风控**

```sql
KEY idx_phone_create (phone, create_time)   -- 同手机号频率限制
KEY idx_ip_create (ip, create_time)         -- 同 IP 刷短信
KEY idx_request_id (request_id)             -- 对账阿里云回执
```

限流判断 `COUNT(*) WHERE phone = ? AND create_time > now()-60s`，联合索引变成一次索引范围扫。

### 6.7 组合索引设计四条通用规律

1. **等值列在前，范围/排序列在后**：B+ 树先按第一列排再按第二列排，等值条件把数据钉在区间后，后面的列才有连续有序性可用；排序列放中间会让等值列失效（阿里规约：等号与非等号混合时，等号列前置）。
2. **组合索引只服务最左前缀，双向查询就建两个**：`group_member` 的 `idx_user_status` / `idx_group_status`、`user_friend` 的两个索引都是同一组列的两种顺序。比建一堆单列索引靠 index merge 合并高效且稳定。
3. **唯一索引兼任业务约束和查询索引**：`uk_user_friend`、`uk_group_user`、`uk_conversation_seq` 既是防脏数据最后防线，本身又是 B+ 树可直接命中等值查询，不需要再为同样条件建普通索引。
4. **每个索引都要说出服务的 SQL**：写多读少的表（`chat_message`）每多一个索引，INSERT 就多维护一棵 B+ 树。该表 4 个索引已接近上限，全部按真实查询路径反推，没有"以防万一"的索引。
