# 05 - 阿里云短信认证服务接口参数

> 来源：阿里云 API 文档（api.aliyun.com）整理，产品 Dypnsapi（云通信号码认证服务）version 2017-05-25。
> 对应实现：`AliyunAuthCodeChannelImpl`（sms.mode=auth）。

## SendSmsVerifyCode（发送验证码）

文档地址：https://api.aliyun.com/document/Dypnsapi/2017-05-25/SendSmsVerifyCode

| 参数 | 类型 | 必填 | 说明 | 本项目处理 |
|---|---|---|---|---|
| PhoneNumber | string | ✅ | 短信接收方手机号 | 入参传入 |
| SignName | string | ✅ | 签名名称。暂不支持自定义签名，用系统赠送签名 | `sms.auth.sign-name`（实测 400 强校验） |
| TemplateCode | string | ✅ | 模板 CODE，赠送签名须搭配赠送模板 | `sms.auth.template-code`（实测 400 强校验） |
| TemplateParam | string | ✅ | 模板参数 JSON。`{"code":"##code##","min":"5"}` 占位符方式由系统动态生成并可核验 | 代码拼接占位符 + 有效期分钟数 |
| SchemeName | string | ❌ | 方案名，不填为"默认方案"，≤20 字符；**不同方案的验证码互相隔离**（实测） | `sms.auth.scheme-name.{scene}`，按场景配置 |
| CountryCode | string | ❌ | 国家编码，默认 86，仅支持国内 | `sms.auth.country-code`（默认 86），发送/核验两侧一致 |
| CodeLength | int | ❌ | 验证码长度 4～8 位，默认 4 | `sms.auth.code-length`（默认 6） |
| CodeType | int | ❌ | 传占位符时必填。1-纯数字 2-纯大写 3-纯小写 4-大小写混合 5-数字+大写 6-数字+小写 7-数字+大小写 | `sms.auth.code-type`（默认 1 纯数字） |
| ValidTime | int | ❌ | 有效时长（秒），默认 300 | `sms.code-expire-seconds` |
| Interval | int | ❌ | 发送间隔频控（秒），默认 60 | `sms.send-interval-seconds`，与应用侧频控一致 |
| DuplicatePolicy | int | ❌ | 重复发送旧码处理：1-覆盖（默认）2-保留（多码均有效） | 不传，走默认 1 覆盖（防多码并存） |
| ReturnVerifyCode | bool | ❌ | 是否在响应中返回验证码 | 不传。验证码不进本服务日志，安全考虑 |
| AutoRetry | int | ❌ | 自动替换签名重试，默认 1 开启 | 不传，走默认 |
| SmsUpExtendCode | string | ❌ | 上行短信扩展码，系统自动生成 | 不接，无需求 |
| OutId | string | ❌ | 外部流水号透传 | 不接，无需求 |

## CheckSmsVerifyCode（核验验证码）

文档地址：https://api.aliyun.com/document/Dypnsapi/2017-05-25/CheckSmsVerifyCode

| 参数 | 类型 | 必填 | 说明 | 本项目处理 |
|---|---|---|---|---|
| PhoneNumber | string | ✅ | 手机号 | 入参传入 |
| VerifyCode | string | ✅ | 用户收到的验证码（发送用占位符方式时阿里云可核验） | 入参传入 |
| SchemeName | string | ❌ | **发送时若传了方案名，核验必须传相同值** | 与发送同源 `sms.auth.scheme-name` ✅ |
| CountryCode | string | ❌ | 默认 86 | 不接 |
| CaseAuthPolicy | int | ❌ | 大小写核验策略：1-不区分 2-区分。仅验证码含字母时有意义 | 不传（验证码纯数字，无意义） |
| OutId | string | ❌ | 外部流水号 | 不接 |

## 返回结构

```json
{
  "AccessDeniedDetail": "无",
  "Message": "成功",
  "RequestId": "CC3BB6D2-...",
  "Model": { "VerifyCode": "4232", "RequestId": "...", "OutId": "...", "BizId": "112231421412414124123^4" },
  "Code": "OK",
  "Success": true
}
```

- HTTP 200 ≠ 发送成功，必须校验 `Success == true`（实现里已处理）
- 发送成功取 `Model.BizId` 落库 `sms_record.biz_id`
- 核验成功取 `Model.VerifyResult == "PASS"`（不通过为 REJECT）

## 常见错误码（HTTP 400）

| 错误码 | 含义 |
|---|---|
| MOBILE_NUMBER_ILLEGAL | 手机号非法 |
| BUSINESS_LIMIT_CONTROL | 当日发送超限 |
| FREQUENCY_FAIL | 发送频率超限 |
| INVALID_PARAMETERS | 参数不合法 |
| FUNCTION_NOT_OPENED | 功能未开通 |

## ⚠️ 出参结构勘误（AI 整理稿 vs 官方/SDK 实测）

网上/AI 整理的接口文档里出参常写成 `Data: {VerifyCode}`（发送）/ `Data: true`（核验），
**这是错的**，与官方文档及本项目的实际运行结果不符。真实出参以 SDK 模型为准
（`SendSmsVerifyCodeResponseBody` / `CheckSmsVerifyCodeResponseBody`，编译期即验证）：

- 顶层是 `Success`（boolean）+ `Code` + `Message` + `RequestId`，业务数据在 **`Model`** 包裹里
- 发送：`Model.BizId` 为回执 ID；`ReturnVerifyCode=true` 时验证码才会在 `Model` 里返回（本项目不开启）
- 核验：`Model.VerifyResult`，`PASS` 通过 / `REJECT` 不通过

判断成败的口径：HTTP 200 ≠ 成功，必须 `Success == true`；核验再叠加 `VerifyResult == "PASS"`。

## 场景隔离实测（2026-11-18）

用两个随手命名的方案（"测试方案A"/"测试方案B"）对同一手机号做对照实验：

| 步骤 | 结果 |
|---|---|
| 方案A 发码 → 立刻用方案B 发码 | 两次都成功，**阿里云没有按手机号跨方案频控** |
| 用方案A 核验方案A的码 | PASS |
| 用方案A 核验方案B的码 | 400 验证失败 |
| 用方案B 核验方案B的码 | PASS |

结论：

1. **SchemeName 就是场景隔离键**：不同方案的验证码互不覆盖、互不能核验
2. 方案名任意字符串即可，**无需控制台预先创建**（本项目按场景直接配 register/login/reset）
3. 发送冷却必须由应用层按场景实现（本项目 Redis key 带 scene）；阿里云侧不会拦跨方案发送

## 关键约定（实现正确性依赖）

1. **方案名一致性**：发送传了 SchemeName，核验必须传相同值——本项目两者同源于 `sms.auth.scheme-name.{scene}`，天然一致
2. **占位符方式才能核验**：发送时 TemplateParam 必须用 `##code##` 占位符（系统动态生成），若自定义验证码值阿里云无法核验——本项目用占位符方式
3. **CodeType 与占位符联动**：传占位符时 CodeType 必填
